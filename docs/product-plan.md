# Homewise プロダクト整理

## 現在の制作範囲（最新の合意）

- 最初は、既存のCodex skillsによる1件の評価結果を見やすいHTMLレポートで表示する。
- 追加費用0円を優先し、ローカルで開く単体HTMLとして試作する。
- 過去の評価物件を横並びにする機能は当面不要。
- 条件や居住年数を画面で変更して再計算する機能も初期対象外。
- オンラインアプリ化は保留。以下のアプリ構想は将来検討する背景として残す。
- `templates/report.html` と `scripts/render_report.py` を実装。`examples/report.json` から `reports/sample.html` を生成する。
- 表示例は既存の過去評価。再調査・計算検証はしておらず、月額の未算入費用や根拠の不整合を明示する。
- 既存skillsのファイルは変更していない。評価結果JSONの生成とHTMLへの自動連携は後続課題。

## これまでに整理したアプリ構想

- 自分用の不動産比較・評価アプリ。
- PCのChromeでの利用を優先する。
- 現在skillsで実行している評価を、簡単に閲覧・比較できるようにする。
- 物件URLを入力し、アプリから新しく調査・評価する方式を採用する。
- 参照する既存スキルは `evaluate-property` と `evaluate-property-single` で確認済み。
- 初期評価モードは単身用（`evaluate-property-single`）。
- 対象サイトはHOME’SとSUUMO。まずHOME’Sの提供URLで取得を検証する。
- 検証用URL： https://www.homes.co.jp/mansion/b-1259230001938/
- 現在のスキル実行環境はCodex。
- 住みやすさと経済性の両方を見て、候補を判断する。
- 居住年数は5年固定にせず、利用者が変更して試算・比較する。
- 希望条件と試算条件はアプリ内で選択・変更する。現時点で本人の条件を固定しない。
- 希望条件に合わない物件も評価し、該当項目に「不一致」と表示する。除外しない。
- 利用者が見つけたURLの物件を評価する。物件検索・おすすめ候補の収集・絞り込みは対象外。

## 参考にする既存処理

ローカルの `life/.claude/skills/evaluate-property/SKILL.md` と
`evaluate-property-single/SKILL.md` を参照。利用中のスキルと一致することを確認済み。
これらは仕様の参考資料として読み、評価処理は実行していない。

- 立地・価格・建物・部屋・流動性の点数と総合評価。
- ローン返済、管理費、修繕積立金、税金、保険等を含む月額。
- 賃貸との費用比較、売却後の手元金、5年間の総コスト。
- 弱気・標準・強気の売却シナリオ。
- 相場の出典・確認日・信頼度、耐震・管理状態などの未確認事項。

## 合意した利用の流れ

1. 自分で見つけたHOME’S・SUUMOの物件URLを入力する。
2. 選択した希望条件・試算条件で、その物件を調査・評価する。
3. 住みやすさと経済性、それぞれの評価と根拠を確認する。
4. 希望条件との不一致を項目ごとに確認する。
5. 評価結果を保存し、必要に応じて過去に評価した物件と横並び比較する。

画面案は「URL入力・条件設定」「評価結果」「保存済み評価」「比較」。配置や分割は未確定。
保存済み評価は自分が入力した物件の履歴であり、検索結果一覧ではない。
既存結果の取り込みは初期版の必須機能には含めない。

## 希望条件と試算条件

次は選択UIの提案。具体的な選択肢・初期値は未確定。

| 種別 | 項目例 | 評価への反映 |
| --- | --- | --- |
| 希望条件 | エリア・駅、面積、間取り、駅徒歩、築年、価格・月額上限 | 指定物件との一致・不一致を表示 |
| 試算条件 | 居住年数、頭金、金利、ローン期間、収入、比較する賃貸費用 | 月額負担、保有期間の総費用、売却後の手元金を計算 |

- 条件は選択式を基本とする。駅の検索選択や金額の自由入力の併用は提案段階。
- 希望条件は物件を自動検索・除外するためには使わない。
- 情報がない項目は「未確認」とし、「不一致」やゼロとは区別する。
- 希望条件への一致と、物件自体の経済性・リスクは分けて表示する。採点への影響は未決定。
- 居住年数に応じて試算期間を変える。長期の売却見通しも確定値として扱わない。

## URL評価の流れ（提案）

1. URLを入力し、単身用の評価条件を確認する。世帯用への対応は後続とする。
2. 物件情報を取得し、取得元URLと取得日時を保存する。
3. 購入・賃貸相場を調査し、根拠となる比較事例を保存する。
4. 選択した居住年数に応じて費用・残債を計算し、希望条件との一致状況と評価を生成する。既存スキルの3シナリオの扱いは仕様を整理する。
5. 結果を保存し、詳細画面と比較一覧に表示する。

実行中は進捗を表示する。取得に失敗した場合は理由と再試行を提示し、
不足項目は手入力で補えるようにする。根拠が不足した評価は暫定として扱う。
AIによる情報整理・定性的評価と、コードによる数値計算を分ける。

## 情報取得の検証状況

- 提供されたHOME’Sページは、この開発環境からの直接HTTP取得で403となった。
- Web閲覧ツールとブラウザ接続ホストは利用できなかったが、ネイティブUI操作による通常のChromeではページを開き、物件概要を読み取れた。
- 403の応答本文はCloudFrontの `Request blocked`。遮断条件の詳細は未特定。
- 続く検証ではUser-Agent・Accept・Accept-Languageをブラウザ相当の値にしたHTTP取得で200となり、HTMLに物件概要が含まれることを確認した。各ヘッダーの寄与は未切り分け。
- `scripts/probe_homes.py` に再実行可能な取得・抽出処理を実装し、同じURLへのライブ接続とJSONへの抽出まで成功。追加のブラウザ連携なしで実装できる可能性がある。
- 確認できた掲載情報：ルピナス大山グランドタワー・iステージ2階、3,400万円、2DK、40.85㎡、2003年10月築、大山駅徒歩6分、管理費14,314円/月、修繕積立金9,234円/月、総戸数50戸。
- 現況は「賃貸中」、その他条件は「オーナーチェンジ」。自宅用評価では居住可否の確認対象として目立つ表示が必要。
- 上記は単一ページ・単一環境での検証。取得スクリプトは動作したが、画面への接続、保存、相場調査、評価計算は未実装。
- URL入力だけで進む体験を優先する。まずHTTP取得を試し、拒否や必須項目の欠落時は明示的に失敗させる。ブラウザ経由は必要な場合の候補とする。貼り付けを標準操作にする案は保留。
- SUUMOは未検証。両サイトとも対応済みとは扱わない。

## データ・計算の設計方針（提案）

- 物件情報、評価結果、家計・ローン条件、出典を分けて保存する。
- 金額の保存単位を円に統一し、表示時に円・万円へ変換する。
- 月々の支払額と、売却・購入諸費用を含む総コスト月額を区別する。
- 不明な値は未確認として表示し、ゼロや推測値で埋めない。
- 各評価に条件と評価日を残し、条件が異なる比較を識別できるようにする。
- 既存スキルの数式や固定値は移植前に検証する。残債は返済総額ではなく元金返済分から算出する。
- 金利・収入・保有期間などは変更可能な条件とし、過去の市場情報を現在値として固定しない。

## 対象外

物件検索、おすすめ候補の自動収集、物件の絞り込み、条件不一致による自動除外。

一般公開、複数ユーザー、スマホ専用UIについても初期対象外を提案しているが、公開・運用範囲は未確定。

## 次に確認すること

1. 利用場所：自分のPC内だけで動かすか、外からもアクセスするか。保存先も合わせて決める。
2. 条件選択の項目と初期値、評価結果で優先して表示する項目。
3. 既存スキルの採点をどこまで引き継ぐか。住みやすさ・経済性の表示と総合評価の関係。
4. Codexでの既存実行を参考に、アプリから利用するAI評価の実行基盤・認証方法・費用を決める。
5. 別のHOME’S物件とSUUMOで取得処理を検証し、対応範囲を定める。

単身用の収入・ローン期間・金利などはアプリ内で設定する。スキル内の数値を本人の現在値とみなさない。

## 実装への進め方

アプリ本体は保留し、現在は冒頭のHTMLレポートを試作する。情報取得スクリプトは技術検証用。

利用場所・保存先 → 条件と評価結果の仕様 → 評価の実行方法 →
技術構成・計算仕様 → 画面と処理の実装、の順で進める。
